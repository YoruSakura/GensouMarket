# Minecraft 插件开发踩坑总结

> 来源：GensouMarket（幻想集市）项目实战经验。适用于 Paper/Spigot 插件 + MySQL 的中大型插件开发。

---

## 1. MySQL 在主线程执行会卡死服务器

**现象**：服务器触发 10 秒无响应警告（Watchdog thread dump），堆栈指向插件的 DB 查询方法，位于 `CraftScheduler.mainThreadHeartbeat` 调用链上。

**原因**：Bukkit 的 `runTask` / `runTaskTimer` 在主线程（Server thread）执行。如果在其中做 MySQL 查询，网络延迟或 MySQL 响应慢时，整个服务器 TPS 归零。

**解决方案**：所有 DB 操作必须在异步线程执行，Bukkit API（经济、背包、发消息）必须回到主线程。推荐三阶段模式：

```java
// 阶段1：异步读 DB
Bukkit.getScheduler().runTaskAsynchronously(plugin, () -> {
    Data data = storage.query(...);

    // 阶段2：回主线程做 Bukkit API
    Bukkit.getScheduler().runTask(plugin, () -> {
        if (!player.isOnline()) return; // 异步期间玩家可能下线
        vault.withdraw(player, cost);
        player.getInventory().addItem(item);

        // 阶段3：异步写 DB（fire-and-forget）
        Bukkit.getScheduler().runTaskAsynchronously(plugin, () -> {
            storage.update(...);
        });
    });
});
```

**易遗漏的主线程 DB 调用点**：
- 界面点击事件处理器（`InventoryClickEvent`）
- 命令处理器（`onCommand`）
- 定时任务（`runTaskTimer` 默认是主线程）
- 玩家登录事件中查邮件/查数据

**定时任务**：用 `runTaskTimerAsynchronously` 替代 `runTaskTimer`。如果任务中有 Bukkit API 调用，在异步任务内部用 `runTask` 回到主线程。

## 2. MySQL 单连接模式不可靠

**现象**：`Communications link failure`、`Read timed out`、`Connect timed out` 持续刷屏。连接断开后无法自动恢复，插件功能全面瘫痪。

**原因**：使用单个 `java.sql.Connection` 长连接。MySQL 的 `wait_timeout`（默认 8 小时）到期后服务端主动断开，插件侧不感知；网络抖动也会导致连接失效。

**解决方案**：使用 HikariCP 连接池。关键配置：

```java
hikariConfig.setMaximumPoolSize(10);       // 最大连接数
hikariConfig.setMinimumIdle(2);            // 最小空闲连接
hikariConfig.setConnectionTimeout(5000);   // 获取连接超时 5s（别设太长）
hikariConfig.setKeepaliveTime(60000);      // 每 60s 发 keepalive 检测死连接
hikariConfig.setMaxLifetime(1800000);      // 连接最大存活 30 分钟后强制回收

// MySQL 驱动层超时（防止 socket 级别阻塞）
hikariConfig.addDataSourceProperty("connectTimeout", "5000");
hikariConfig.addDataSourceProperty("socketTimeout", "5000");
```

每次操作从池中获取连接，用完归还（try-with-resources）：

```java
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {
    // ...
} catch (SQLException e) {
    logThrottled("操作失败", e); // 限流日志
}
```

## 3. HikariCP 运行时不一定可用

**现象**：`NoClassDefFoundError: com/zaxxer/hikari/HikariConfig`。编译通过但运行时类找不到。

**原因**：标准 Paper 服务端内部使用 HikariCP，但插件的 ClassLoader 不一定能访问到服务端内部类。某些 Paper 分支（如 Leaf）或特定版本可能不暴露 HikariCP 给插件。`compileOnly` 依赖不会打包进 jar。

**解决方案**：将 HikariCP 通过 Shadow/Fat Jar 打包进插件：

```groovy
plugins {
    id 'com.github.johnrengelman.shadow' version '8.1.1'
}

dependencies {
    implementation 'com.zaxxer:HikariCP:6.2.1'  // 用 implementation，不是 compileOnly
}

// Shadow 会将 HikariCP 打包进最终 jar
```

或者使用 `relocate` 避免与其他插件的 HikariCP 冲突：

```groovy
shadowJar {
    relocate 'com.zaxxer.hikari', 'net.yourplugin.libs.hikari'
}
```

## 4. DB 错误日志刷屏

**现象**：MySQL 连接异常时，每秒数十条完整堆栈 WARNING 刷满控制台，淹没其他日志。

**解决方案**：实现限流日志，同类错误在时间窗口内只输出一次：

```java
private final AtomicLong lastErrorLog = new AtomicLong(0);
private static final long LOG_THROTTLE_MS = 30_000;

private void logThrottled(String message, Exception e) {
    long now = System.currentTimeMillis();
    long last = lastErrorLog.get();
    if (now - last > LOG_THROTTLE_MS && lastErrorLog.compareAndSet(last, now)) {
        logger.log(Level.WARNING, message, e);
    }
}
```

## 5. 界面操作需要二次确认防误触

**现象**：玩家在界面中手滑点击导致意外购买/出售，引发纠纷。

**解决方案**：首次点击显示确认提示，限时内再次点击同一目标才执行：

```java
private record PendingAction(String type, int targetId, long timestamp) {}
private final Map<UUID, PendingAction> pending = new ConcurrentHashMap<>();

private boolean checkConfirmation(Player player, String action, int targetId, String msg) {
    UUID uuid = player.getUniqueId();
    PendingAction p = pending.get(uuid);
    long now = System.currentTimeMillis();
    if (p != null && p.type().equals(action) && p.targetId() == targetId
            && (now - p.timestamp()) < 5000) {
        pending.remove(uuid);
        return true; // 确认通过
    }
    pending.put(uuid, new PendingAction(action, targetId, now));
    MessageUtil.send(player, msg); // "再次点击确认..."
    return false;
}
```

## 6. 异步回调中玩家可能已下线

**现象**：异步 DB 操作完成后回到主线程，调用 `player.getInventory()` 时 NPE 或操作无效。

**原因**：异步操作期间（哪怕只有几毫秒）玩家可能已下线，`Player` 对象变为无效状态。

**解决方案**：每次从异步回到主线程时，第一行检查 `player.isOnline()`：

```java
Bukkit.getScheduler().runTask(plugin, () -> {
    if (!player.isOnline()) return; // 必须检查
    // 安全地操作背包/经济/发消息...
});
```

## 7. 跨服共享 MySQL 不等于跨服实时同步

**现象**：多个子服共享同一个 MySQL 数据库，数据写入能互相看到，但玩家体验不实时——卖家金币不即时到账（需手动领取）、拍卖状态在另一服上不刷新。

**原因**：MySQL 只是共享存储，没有主动通知机制。各子服只在自己的定时任务或玩家操作时才读取 DB。

**解决方案**：需要跨服事件广播层。两种方案：

| 方案 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **Velocity 插件消息通道** | 单 Velocity 代理下的群组服 | 零额外依赖，实现简单 | 依赖代理在线，不支持跨代理 |
| **Redis Pub/Sub** | 多代理/大规模集群/需要外部系统集成 | 代理无关，可持久化 | 需运维 Redis |

广播内容不是数据本身（数据在 MySQL），而是事件通知："某物品被买了"、"拍卖有新出价"。接收方收到后刷新界面或发送聊天提示。

## 8. Vault 经济 API 必须在主线程调用

**现象**：异步线程中调用 `economy.withdrawPlayer()` 导致数据不一致或异常。

**原因**：Vault 是 Bukkit 插件，底层经济插件（如 Essentials、CMI）通常不是线程安全的。

**解决方案**：所有 `vault.withdraw()` / `vault.deposit()` / `vault.has()` 调用必须在主线程。这是三阶段异步模式中"阶段2 回主线程"的核心原因之一。

## 9. 插件项目拆分为多子项目时的 Gradle 配置

**现象**：IDEA 打开项目根目录后找不到 Gradle 项目，无法识别子目录中的独立 Gradle 构建。

**解决方案**：在项目根目录创建 `settings.gradle`，使用 `includeBuild` 注册各子项目：

```groovy
rootProject.name = 'MyProject'
includeBuild('MyProject-plugin')
includeBuild('MyProject-velocity')
```

这样各子项目保持独立 Gradle 构建（各自的 `build.gradle`、`gradlew`），IDEA 能同时识别所有子项目。不要用 `include`（那是多模块共享构建），用 `includeBuild`（组合构建，互相独立）。

## 10. Paper 插件中必须使用 Adventure API 替代已弃用的 Bukkit API

**现象**：IDEA 大量警告 `'org.bukkit.ChatColor' 已弃用`、`'setDisplayName(String)' 已弃用`、`'setLore(List<String>)' 已弃用`、`'createInventory(holder, size, String)' 已弃用`。

**原因**：Paper 1.16+ 原生支持 Adventure API，旧的 `ChatColor`、`String` 类型的 `setDisplayName`/`setLore` 等被标记为弃用。

**解决方案**：

```java
import net.kyori.adventure.text.Component;
import net.kyori.adventure.text.format.NamedTextColor;
import net.kyori.adventure.text.serializer.legacy.LegacyComponentSerializer;

// 序列化器常量（legacyAmpersand 直接解析 & 颜色码）
private static final LegacyComponentSerializer LEGACY = LegacyComponentSerializer.legacyAmpersand();

// Inventory 标题: String → Component
Inventory inv = Bukkit.createInventory(holder, 54,
    Component.text("标题", NamedTextColor.GOLD));

// ItemMeta displayName: setDisplayName(String) → displayName(Component)
meta.displayName(LEGACY.deserialize("&6&l金色粗体名称"));

// ItemMeta lore: setLore(List<String>) → lore(List<Component>)
List<Component> lore = new ArrayList<>();
lore.add(LEGACY.deserialize("&7灰色描述"));
lore.add(Component.empty()); // 空行
meta.lore(lore);

// 读取现有 lore: getLore() → lore()
List<Component> existing = meta.lore(); // 返回 List<Component> 或 null

// ChatColor.translateAlternateColorCodes 替代方案:
LegacyComponentSerializer ampersand = LegacyComponentSerializer.legacyAmpersand();
LegacyComponentSerializer section = LegacyComponentSerializer.legacySection();
String colored = section.serialize(ampersand.deserialize("&a绿色文字"));
```

**注意**：`legacyAmpersand()` 解析 `&` 前缀，`legacySection()` 解析 `§` 前缀。如果源字符串用 `&`，直接用 `legacyAmpersand().deserialize()` 即可，不需要先 `ChatColor.translateAlternateColorCodes` 再转。

## 11. 布尔配置方法命名与逻辑方向必须一致

**现象**：`isXxxEnabled()` 返回 `true` 时代码却执行了"禁用"逻辑（返回默认值/跳过计算）。运行时功能开关完全反转——配置启用时实际禁用，禁用时反而启用。

**原因**：写代码时条件判断方向搞反了：

```java
// 错误：enabled 为 true 时返回 1.0（无波动），反了！
public double calculate(String itemId, long timeMillis) {
    if (config.isMarketFluctuationEnabled()) {
        return 1.0; // 这里应该是 !enabled
    }
    // ... 实际计算 ...
}
```

**解决方案**：
```java
// 正确：not enabled 时返回默认值
if (!config.isMarketFluctuationEnabled()) {
    return 1.0;
}
```

**预防**：IDEA 会提示"始终反转对布尔方法的调用"——这个警告往往暗示逻辑反了，不要忽略。

## 12. 不要用 sed 替换 Java 源文件

**现象**：使用 `sed -i` 批量替换 Java 文件内容后，文件被清空为 0 字节，代码丢失。

**原因**：`sed` 的工作目录、文件路径、权限等问题可能导致意外截断。尤其是在 IDE 远程项目、Docker 挂载卷等环境下，`sed -i` 的原子性无法保证。

**解决方案**：对 Java 源文件永远使用编辑器/IDE 的查找替换功能，或使用专门的代码编辑工具（如 Edit tool）。如果必须用命令行，先备份：

```bash
cp MyFile.java MyFile.java.bak
sed -i 's/old/new/g' MyFile.java
# 验证后再删除备份
```

## 13. File.delete() / File.renameTo() 返回值必须检查

**现象**：IDEA 警告 `'File.delete()' 的结果已忽略`、`'File.renameTo()' 的结果已忽略`。

**原因**：这两个方法失败时不抛异常，只返回 `false`。忽略返回值意味着文件操作可能静默失败。

**解决方案**：
```java
// 错误
backupFile.delete();
configFile.renameTo(backupFile);

// 正确
if (backupFile.exists() && !backupFile.delete()) {
    logger.warning("无法删除旧备份文件");
}
if (!configFile.renameTo(backupFile)) {
    logger.severe("无法备份配置文件，操作中止");
    return false;
}
```

## 14. getString() 返回值可能为 null

**现象**：`NullPointerException` 在 `UUID.fromString(sec.getString("seller-uuid"))` 处崩溃，或 `Material.matchMaterial(null)` 返回 null 导致后续 NPE。

**原因**：Bukkit `ConfigurationSection.getString()` 和 JDBC `ResultSet.getString()` 在 key 不存在或值为 null 时返回 null。直接传入 `UUID.fromString()` / `Material.matchMaterial()` 会 NPE。

**解决方案**：
```java
String sellerUuid = sec.getString("seller-uuid");
if (sellerUuid == null) continue; // 或 return null
l.setSellerUuid(UUID.fromString(sellerUuid));

String matName = sec.getString("material");
if (matName == null) continue;
Material mat = Material.matchMaterial(matName);
if (mat == null) continue;
```

## 15. 定时扫描不能替代主动触发机制

**现象**：拍卖到期后不会自动结算，必须玩家手动进入界面点击对应物品才触发退回/发放。定时任务每分钟扫描一次，但玩家体验是"必须手动点一下"。

**原因**：仅依赖定时扫描（如每 60 秒检查一次过期拍卖）存在延迟窗口。玩家在拍卖到期后立即打开界面，此时定时任务还没跑到，状态未更新。界面代码中又没有主动检查到期逻辑，导致必须等下一次扫描或手动点击才触发。

**解决方案**：使用内存定时器驱动 + 兜底扫描双保险：

```java
// 创建拍卖时注册延迟任务
private final Map<Integer, Integer> scheduledTasks = new ConcurrentHashMap<>();

long delayTicks = durationMinutes * 60 * 20L;
int taskId = Bukkit.getScheduler().runTaskLaterAsynchronously(plugin, () -> {
    Auction auction = storage.getAuction(id);
    if (auction != null && auction.getStatus() == Auction.Status.ACTIVE) {
        endAuctionAsync(auction);
    }
    scheduledTasks.remove(id);
}, delayTicks).getTaskId();
scheduledTasks.put(id, taskId);

// 启动时恢复活跃拍卖的定时任务
public void restoreActiveAuctions() {
    List<Auction> active = storage.getActiveAuctions();
    long now = System.currentTimeMillis();
    for (Auction auction : active) {
        long remaining = auction.getEndTime() - now;
        if (remaining <= 0) {
            Bukkit.getScheduler().runTaskAsynchronously(plugin, () -> endAuctionAsync(auction));
        } else {
            long delayTicks = remaining / 50;
            int taskId = Bukkit.getScheduler().runTaskLaterAsynchronously(plugin, () -> {
                // 到期时自动结算
            }, delayTicks).getTaskId();
            scheduledTasks.put(auction.getId(), taskId);
        }
    }
}
```

**关键点**：
- 主触发：创建拍卖时注册 `runTaskLaterAsynchronously`，到期自动执行
- 兜底：保留定时扫描（每分钟），覆盖重启/异常中断等情况
- 启动恢复：服务器重启后从 DB 读取活跃拍卖，重新注册定时任务
- 任务清理：取消拍卖时从 Map 中移除并 `cancelTask`

## 16. 余额判断方法名与返回语义必须一致（最容易引发“有钱判没钱”）

**现象**：玩家 `bal/money` 明确充足（如 10000+），购买/出价仍提示余额不足；甚至触发异常回滚（误下架/误退回）。控制台无报错，看起来“逻辑执行正确但结果错误”。

**原因**：经济封装层方法名与语义反了（例如 `has()` 实际返回 `!economy.has(...)`），调用方再按“正常语义”写判断后，整体逻辑双重反转或单次反转。

**解决方案**：
1. 统一语义：`has(player, amount)` 必须是“余额充足返回 true”。
2. 全局审计所有调用点，禁止遗留“按旧反语义写的 if 分支”。
3. 先跑两条烟雾测试再继续回归：
   - 余额 20000 购买 1000：必须成功
   - 余额 0 购买 1000：必须失败且不改坏商品状态

## 17. 扣款失败只应失败交易，不能联动触发商品过期/下架

**现象**：买家在确认前余额被改为不足后，购买失败同时卖家物品被立刻“过期返还/下架”。

**原因**：失败回滚路径和状态机耦合错误，把“购买失败”错误映射到“商品生命周期结束”。

**解决方案**：
- 明确状态机：购买失败 == 保持 `ACTIVE`（可继续售卖），不是 `EXPIRED/CANCELLED`。
- 回滚顺序固定：
  1) 扣款失败 -> 终止交易
  2) 不发物
  3) 不改 listing 状态
  4) 给买家提示余额不足
- 为该场景加专项回归（余额边界 + 二次购买验证）。

## 18. 跨服资金链路要避免“即时到账 + 邮箱补偿”双发

**现象**：同一笔收入可能同时发生“在线即时到账”与“邮箱入账补偿”，造成重复发放。

**原因**：跨服到账与补偿路径缺乏互斥/确认闭环；未严格区分“已成功执行”与“需要补偿”。

**解决方案**：
- 先判定并锁定“本次发放策略”（即时 or 邮箱），同一 requestId 只允许一种落地结果。
- 引入 ACK/FAIL 闭环：目标服 `deposit` 成功才 ACK；失败才走邮箱补偿。
- `collect` 作为兜底，不应再领取已即时发放的同笔数据。

## 19. 在线退款（被超价/取消拍卖）体验不能退化为“仅邮箱”

**现象**：玩家在线时被超价或拍卖取消，本应即时退款却只进邮箱，且缺少提醒，用户感知为“钱丢了”。

**原因**：跨服退款通知链路与到账链路未保证在线优先；提醒发送与资金发放脱钩。

**解决方案**：
- 在线优先策略：在线玩家先即时退款并提示；仅失败时写邮箱。
- 到账与提醒绑定：退款成功必须伴随可见提示。
- 补测矩阵至少覆盖：
  - 被超价退款（在线）
  - 取消拍卖退款（在线）
  - `collect` 防重复
